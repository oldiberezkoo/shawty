# SHAWTY

Платформа управления цифровыми экранами: кампании с расписанием, публикация
контента на телевизоры с подтверждением фактической доставки.

Полный план работ и архитектурные решения — в [`PLAN.md`](./PLAN.md).

---

## Что уже работает

- **Дашборд**: вход, роли и область доступа, список экранов с состоянием сети.
- **Привязка телевизора по QR**: короткоживущий код, одноразовое подтверждение,
  ограничение частоты, проверка лимита тарифа, отдельные учётные данные устройства.
- **Канал устройства**: WebSocket с авторизацией по короткоживущему токену,
  heartbeat, подтверждение применения публикации.
- **Управление экранами**: отключение, отвязка, ротация секрета без визита к ТВ.
- **Кампании и расписание**: даты, приоритет, области показа, окна по дням недели
  и часам, часовой пояс филиала, согласование перед запуском.
- **Автоматическая смена программы**: фоновая публикация в момент, когда окно
  кампании начинается или заканчивается. Телевизор узнаёт момент смены заранее
  и готовит следующую программу до переключения.
- **Календарь показа**: что и когда идёт на каждом экран��, и кто мог бы пойти
  вместо этого.
- **Мониторинг**: интервалы простоя, лента событий, доступность за период по трём
  уровням — «на связи», «на связи со старым контентом», «недоступен» — и CSV.
- **Журнал действий**: кто и когда отвязывал экраны, удалял файлы, согласовывал
  кампании и публиковал контент.
- **Отчёт по кампаниям**: охват, применение, подтверждённые старты и время
  показа — с точной привязкой к кампании, а не по датам.
- **Команда**: приглашение по одноразовой ссылке, регистрация прямо по ней,
  смена роли и приостановка сотрудников, матрица прав в интерфейсе.
- **Тариф и потребление**: сколько экранов, сотрудников и места осталось,
  предупреждение об истечении подписки поверх всех экранов.
- **Интерфейс, который переносится с телефона на монитор**: боковая навигация
  с иконками, таблицы сворачиваются в карточки по ширине контейнера, на узком
  экране меню выезжает поверх страницы, поля не разъезжаются при вводе с
  телефона.
- **Оформление уровня продуктового приложения**: Inter с кириллицей, слоистые
  поверхности и короткие анимации (отключаются системной настройкой), единые
  заголовки, пустые состояния с выходом и уведомления со значком тона.

## Стек

| Слой | Решение |
|---|---|
| Фреймворк | Next.js 16 (App Router), React 19, TypeScript 5.9 |
| База | SQLite через `better-sqlite3` + Drizzle ORM, режим WAL |
| Интерфейс | Tailwind CSS 4, headless-компоненты Base UI (`@base-ui/react`) |
| Канал | `ws`, один порт вместе с Next |
| Медиа | ffmpeg / ffprobe |

## Требования

- Node.js ≥ 20.9 (проверено на 26.5)
- pnpm 11
- ffmpeg и ffprobe в `PATH` (нужны с этапа P2)

## Запуск

```bash
pnpm install
pnpm db:migrate          # применить миграции
pnpm db:seed             # демо-данные
pnpm dev                 # http://localhost:3000 (и watcher контрактов)
```

Демо-вход: `owner@shawty.uz` / `demo1234`

## Проверки

```bash
pnpm check               # типы + все тесты
pnpm test                # домен и интеграция с настоящей базой
pnpm smoke:pairing       # сквозной протокол привязки: HTTP + WebSocket + база
pnpm smoke:schedule      # сквозная проверка кампаний и расписания
pnpm smoke:pages         # все страницы дашборда отдаются с живыми данными
```

Сквозные проверки требуют запущенного `pnpm dev` и самостоятельно убирают
за собой тестовые экраны.

## Структура

```
apps/web/              Next.js: страницы, компоненты, клиент API
apps/web/src/          пока здесь же исторический бэкенд (переедет в apps/api)
apps/web/server/       текущий композитный сервер: Next + WebSocket на одном порту
apps/api/              Hono + ws + Drizzle + SQLite (Фаза 2)
packages/contracts/    общие схемы, DTO и кадры WebSocket
infra/                 reverse-proxy и упаковка (Фаза 5)
data/                  SQLite, медиа и секреты (gitignored)
```

Правило: `src/domain` не знает про Next и базу. Там чистые функции, которые
тестируются без моков. После разделения `apps/web` не сможет импортировать
код бэкенда — только `@shawty/contracts`.

## Настройки окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `3000` | Порт сервера |
| `PUBLIC_URL` | `http://localhost:3000` | Адрес, попадающий в QR. **На телевизоре должен быть доступен из сети.** |
| `SERVER_SECRET` | создаётся в `data/.secret` | Ключ HMAC для кодов привязки и секретов устройств. В продакшене задать явно |
| `PAIRING_QR_CARRIES_CODE` | `false` | `true` — код попадёт прямо в QR (быстрее, слабее) |
| `PAIRING_CODE_TTL_MS` | `300000` | Срок кода подтверждения, 5 минут |
| `PAIRING_MAX_ATTEMPTS` | `8` | Попыток ввода кода до блокировки сессии |
| `PLAYER_OFFLINE_AFTER_SEC` | `90` | Порог «нет связи» |
| `PLAYER_SCHEDULE_HORIZON_DAYS` | `7` | Горизонт расписания, закладываемый в манифест |
| `PLAYER_PREFETCH_BEFORE_MS` | `600000` | За сколько до смены программы экран готовит публикацию |
| `DEVICE_ACCESS_TOKEN_TTL_MS` | `900000` | Срок токена устройства |

Полный список — в `src/config/server.ts`.

Важно: это зона **филиала**. Компания одна, а филиалы в разных зонах — окно
«с 09:00» в них наступает в разное время.

## Важные решения

**Никаких постоянных токенов в URL.** Адрес попадает в историю браузера,
логи и стороннюю аналитику. Устройство обменивает секрет на короткоживущий
токен, а WebSocket принимает токен первым кадром, не в адресе.

**Код подтверждения не в QR по умолчанию.** QR несёт только идентификатор
сессии, а восьмизначный код человек вводит руками. Тот, кто просто
сфотографировал экран, не сможет ни подтвердить привязку, ни перехватить
устройство: для обмена требуется локальный nonce, который телевизор никогда
не показывает.

**Данные одной компании недоступны другой.** Проверка идёт на уровне запроса,
а не фильтрацией результата.

**Что показывается, решает сервер.** Плеер не знает про кампании, приоритеты и
пересечения окон: два телевизора с чуть разными версиями плеера показывали бы
разное в один и тот же момент. Сервер отдаёт готовую программу и момент
следующей смены, а экран готовит следующую публикацию заранее.

**Окна считаются в часовом поясе филиала.** «С 09:00» в Самарканде и в Ташкенте —
это разное время, хотя цифры выглядят одинаково. Перевод стрелки проверяется
тестами на реальных зонах.

**Простой считается от последнего heartbeat, а не от момента обнаружения.**
Насос замечает обрыв с задержкой до интервала проверки; если считать от
момента обнаружения, отчёт сдвинет время недоступности и он перестанет
сходиться с журналом устройства.

**Три уровня достоверности, и третий не утверждается.** Доступен экран — показывает
ли он нужную публикацию — видел ли это человек. Камер и датчиков внимания нет,
поэтому счётчика показов в продукте нет и не будет. В выгрузках колонка названа
`started_plays`, а не `views`.

**Журнал действий пишется в сервисе, а не в маршруте.** Иначе отвязка экрана из
скрипта прошла бы без следа, а журнал выглядел бы полным. Фоновая публикация по
расписанию в журнал не пишется: её никто не инициировал.
